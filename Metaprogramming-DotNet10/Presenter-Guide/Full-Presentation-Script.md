# Part 1 — Understanding Metaprogramming — 4:30 of slide time

## Slide 3 — What is metaprogramming? · 1:00

**Visual:** bullets left, six-line code box right, blue "why it works" bar below.

**Say:**

> Normal programming: your code operates on data. Metaprogramming: your code operates on
> the program itself. "Meta" means "about" — programming about programs.

**Code:**

> Top half: `customer.Email`. I wrote that name; the compiler checked it.
>
> Bottom half: ask the object for its type, ask the type for a property called "Email",
> read the value. The property name is now *data* — it could come from a config file or an
> HTTP request.
>
> And if I typo "Emial" in the bottom version, it still compiles. It returns null at
> runtime. Hold that thought — it's the central trade of this whole session.

**Say (the blue bar — verbatim):**

> Why is this possible at all? When the compiler builds your DLL it writes two things: the
> IL, and metadata tables describing every type, method and attribute you declared. That
> metadata isn't debug info and isn't optional — the runtime needs it. Reflection isn't
> magic; it reads a table of contents that was always there.

**Spare 10 s:**

> And this isn't `dynamic`. With `dynamic` you still write the member name in source. Here
> the name itself is data.

**Visual:** diagram `03`, full slide.

**Say:**

**Visual:** code, real console output, flags table, amber box, red box.

## Slide 14 — Attributes and custom attributes · 1:30

**Visual:** diagram `07`; code and validation output; `AttributeUsage` table; the

**Say:**

> Start with the red line in the diagram, because it's the commonest misconception.
>
> **(verbatim)** An attribute does nothing. It's inert data until something reads it.

# Part 3 — Runtime Code Generation — 12:00

## Slide 16 — What is runtime code generation? · 1:00

**Visual:** bullets; the two `RuntimeFeature` flags; platform table; amber library rule.

**Say:**

> Part 2 read a description that was already there. Part 3 writes code that wasn't.
>
> There's exactly one good reason. Reflection is slow *per call*, because every call re-does
> binding and access checks. If you'll do the same reflective operation a million times, pay
> the reflection *once* to generate a specialised method, then call that. You convert a
> per-call cost into a one-off cost. That's the reason.
>
> And one structural reason: a mock must *be* an `IFoo` to be passed where an `IFoo` is
> expected. No amount of reflection creates a type. Only code generation does.
>
> Then the table — which decides whether any of Part 3 is available to you. Two flags, and
> they differ. *Supported*: can I create code at all? False under Native AOT — Emit throws.
> *Compiled*: will it be JIT-compiled? False on the Mono interpreter, so on iOS it works but
> runs interpreted — and the entire speed benefit, the only reason you did it, disappears.

**Transition:**

> Before the IL, let's be precise about how the two APIs differ.

## Slide 17 — Reflection vs Reflection.Emit · 1:20

**Visual:** diagram `09`; comparison table beneath.

**Say:**

> Top lane, reflection. Every call binds arguments, runs access checks, boxes things. The
> work *repeats*. Measured here: about seven to eight times a direct property access.
>
> Now defuse that immediately. Look at the units — sixty-seven milliseconds for *two
> million* reads. Thirty-three nanoseconds per call. Once per web request, it's free. Per
> row of a million-row import, it's your bottleneck.
>
> **(verbatim)** "Reflection is slow" is true per call, and frequently irrelevant.
>
> Bottom lane: the work happens once. After that you're calling a delegate — 1.2 times
> direct. Same speed class as hand-written code.
>
> And here's the finding that surprised me when I measured it.
>
> **(verbatim)** A cached delegate from `MethodInfo.CreateDelegate` was *exactly* as fast as
> the emitted IL. Identical. So before you write a single OpCode — try `CreateDelegate`. You
> get emit-level speed with none of the risk, and code your colleagues can read.
>
> Last row reframes it: these aren't rivals. Reflection finds the target; Emit bakes it in.

## Slide 18 — Introduction to CIL / MSIL · 1:30

**Visual:** diagram `10` — pipeline, three branches.

**Say:**

> C# through `csc`, out comes IL plus metadata — and note your DLL contains *both*. Part 2
> read the metadata box; Part 3 writes into the IL box. At runtime the JIT compiles IL to
> machine code, per method, on first call.
>
> Why the extra step? One assembly runs on x64 and Arm64, Windows, Linux and macOS. The JIT
> specialises for the actual CPU — it can use AVX-512 on a machine that has it without you
> shipping a separate build. And because IL is typed and verifiable, the runtime can enforce
> memory safety.
>
> CIL, MSIL, IL — three names, one thing. Stack-based, CPU-independent, fully typed.
> ECMA-335.
>
> Then three branches, because the simple story isn't the whole story.
>
> Native AOT: compiled fully ahead of time, no JIT ships — so runtime code generation is
> impossible there. That's the constraint from the last slide, now with a reason.
>
> ReadyToRun: precompiled at publish, IL kept as a fallback. Faster startup; the JIT can
> still re-optimise.
>
> Mono interpreter: IL interpreted, never compiled.

**Spare 10 s:**

> And tiered compilation means a hot method gets compiled more than once — quickly first,
> then optimised. It's why benchmark warm-ups matter.

**Transition:**

> So what does IL look like? It's a stack machine.

## Slide 19 — IL instructions and the evaluation stack · 2:00

**Visual:** diagram `11` — four columns, instruction and resulting stack. Instruction strip
beneath.

> **Do not rush this slide. If the room leaves understanding only this, Part 3 worked.**

**Say:**

> Four columns. Watch the stack.
>
> `ldarg.0` — push argument zero. Stack holds `a`.
>
> `ldarg.1` — push argument one. Stack holds `a`, then `b` on top.
>
> `add` — pop two, push their sum. Stack holds `a + b`.
>
> `ret` — pop the return value and return. Stack empty.
>
> That is a complete method. `int Add(int a, int b)`. Four instructions.
>
> There are no registers you can name in IL — everything goes through this one stack.
>
> Now the two rules at the bottom. Hear them as a debugging tool, not trivia.
>
> **(verbatim)** Rule one: at `ret`, the stack holds exactly the return value. Leave
> something behind and the IL is invalid. Rule two: operand types must suit the opcode.
>
> Nearly every Emit bug you'll write violates one of those. Which is why I write the
> expected stack state as a comment on every `Emit` line — it turns an invisible bug into a
> visible one.
>
> And one numbering detail, which catches everybody once.
>
> **(verbatim)** In a *static* method, `ldarg.0` is the first argument. In an *instance*
> method, `ldarg.0` is `this`, and the first argument is `ldarg.1`. If your generated method
> returns nonsense, check that first.
>
> The strip at the bottom is the instruction set for this session. Eight instructions —
> genuinely enough to follow all of Part 3. The goal is recognition, not recall.

## Slide 20 — DynamicMethod, ILGenerator, CreateDelegate · 1:40

**Visual:** diagram `12` — six boxes, a red warning, an amber warning, a findings bar.

**Say:**

> Six steps. Declare the signature. Get the IL writer. Emit instructions. `CreateDelegate`
> hands the IL to the runtime and gives you something callable. The JIT compiles it on the
> *first* call. After that, a cached delegate at roughly direct speed.
>
> Two warnings — and notice where the first sits. Invalid IL is detected at the *JIT* step.
> Not at `Emit`, not at `CreateDelegate`. On the first call. So a bug in your IL surfaces a
> long way from the line that wrote it.
>
> Second warning — the mistake that makes the whole technique backfire.
>
> **(verbatim)** Cache the delegate. I've seen code that builds a `DynamicMethod` inside the
> method it's trying to speed up. That is slower than the reflection it replaced — strictly
> worse on every axis. Generate once. Cache. Reuse.
>
> Then the findings bar, which was the most sobering thing I found preparing this.
>
> I tested two broken methods on .NET 10. A missing `ret` threw `InvalidProgramException` on
> first call — fine, a clear failure. But `add` on an int and a string threw *nothing*. It
> returned a plausible-looking number, the same number twice. It was the string's managed
> reference, added to one, as an integer.
>
> **(verbatim)** Fully-trusted `DynamicMethod` IL is not type-verified. Your safety net is
> thinner than the C# compiler's, and sometimes there is no net at all.

## Slide 22 — AssemblyBuilder → MethodBuilder · 1:30

**Visual:** diagram `13`; amber correction at the bottom.

**Say:**

> This is Part 2's hierarchy, built in reverse. Part 2 read Assembly, Type, Member. Here we
> *write* it: `AssemblyBuilder`, `ModuleBuilder`, `TypeBuilder`, then fields, constructors,
> methods and properties — each with its own `ILGenerator`.
>
> One rule governs all of it. `CreateType()` bakes the type. Before that call it doesn't
> exist and can't be instantiated. After it, nothing more can be added.
>
> Now look at `AddInterfaceImplementation`, because this is the pattern that makes the whole
> thing practical.
>
> **(verbatim)** Generate a type that implements an interface you already know, then talk to
> it through that interface. Reflection is used once, at creation. Never on the hot path.
>
> That's not a trick — it's exactly how Moq, NSubstitute, Castle DynamicProxy and EF Core's
> lazy-loading proxies all work.
>
> Then the amber bar, which corrects material you may have read.
>
> **(verbatim)** On .NET 10, `AssemblyBuilderAccess` has exactly two members: `Run` and
> `RunAndCollect`. `Save` and `RunAndSave` were .NET *Framework* members. They do not exist.
> A tutorial calling `DefineDynamicAssembly` with `RunAndSave` and then `.Save` does not
> compile on modern .NET at all. I checked by printing the live enum members — and the demo
> does that on screen.
>
> Good news: saving *is* supported, through a different class.

## Slide 23 — Generating types and methods at runtime · 1:00

**Visual:** `TypeBuilder` code left; output including the persisted DLL right; amber
`ldarg.0` callback.

**Say:**

# Part 4 — Real-World Applications — 7:30 of slide time

## Slide 24 — ASP.NET Core MVC and dependency injection · 2:15

**Visual:** diagram `18` — startup lane, request lane, the blue thesis bar.

**Say (MVC):**

> You write `ReportsController` with `[HttpGet]` on a method. `Program.cs` has one relevant
> line — `AddControllers()` — and it names no controller. So how does the framework find
> yours?
>
> Application parts are the search path — by default the entry assembly. Add a part and MVC
> finds controllers in another DLL; that's how a plugin contributes endpoints.
>
> Then it scans for types. The rule: it's a controller if it carries `[ApiController]` or
> `[Controller]`, *or* if its name ends with "Controller". Notice what's *not* in that rule —
> inheriting from `ControllerBase`. That surprises people.
>
> Then it reads `[HttpGet]` and `[Route]` into an `ActionDescriptor` table.

**Say (DI):**

> Dependency injection, and the single insight is this.
>
> **(verbatim)** A constructor signature *is* a machine-readable dependency list. Nobody
> wrote a config file saying `OrderService` needs a repository and a clock. The constructor
> already says so — and the constructor is already in metadata. That's the whole idea.
>
> Two things, then move on. Lifetimes: singleton, scoped — per HTTP request — and
> transient. The classic bug is a singleton capturing a scoped service; `ValidateScopes`
> turns that into an exception instead of a slow leak. And the container picks the greediest
> *satisfiable* constructor — so adding a registration elsewhere can change which one runs.

**Say (precision — verbatim):**

> You'll hear "DI uses Reflection.Emit". I read the provider's private engine field on
> .NET 10 — it's `DynamicServiceProviderEngine`, which picks a strategy at runtime: a
> reflection engine first, a faster compiled one once a service is resolved enough times,
> reflection-only under AOT. So "DI uses reflection" is the safe claim. Anything more
> specific depends on the container, its version and the platform.

**Say (the thesis — verbatim):**

> And land the blue bar. Reflection at *startup*. Per request, a table lookup and a cached
> delegate. Discover once, cache, then execute compiled code. Which is why "MVC uses
> reflection so it must be slow per request" is simply wrong.

## Slide 25 — Entity Framework Core and serialization · 2:00

**Visual:** EF LINQ and generated SQL left; the JSON table and measurement box right.

**Say (EF Core):**

> Three lines of LINQ. And *that* is the SQL EF produced. The navigation became an inner
> join, the nullable one a left join, the anonymous type a select list. It never loaded a
> whole `Post`.
>
> How? `IQueryable`'s `Where` takes `Expression<Func<T,bool>>`, not `Func<T,bool>`. The
> query arrives as *data*, and EF runs a chain of expression visitors over it until it can
> be printed as SQL.
>
> Now the precision point. The EF model is *not* your classes.
>
> **(verbatim)** It's a separate, richer model that EF builds by reading your CLR metadata.
> The proof is a shadow property: a property in EF's model with no C# property at all. A
> column in the database, nothing to assign in your class. Reflection is the input; the
> model is the output.
>
> And look at the amber note. `string.Contains` became `instr(...)` — a SQLite function, not
> `LIKE`. The *provider* chooses the translation; SQL Server emits something different for
> the same C#. So read the SQL your provider actually produces. That's what `ToQueryString`
> is for.

**Say (serialization):**

> Serialization: same job, two mechanisms — slide 6 made concrete. "Byte-for-byte identical:
> True." Same input, same output. The only difference is *when* the metaprogramming ran.
>
> And the right-hand column is why source generation exists: no startup cost,
> trimming-safe, and it works under Native AOT where reflection mode doesn't.

**Spare 25 s (cut this first if behind):**

> One correction. The usual advice is "reuse your `JsonSerializerOptions`, otherwise it
> re-reflects every call". I measured it three ways. New-but-identical options is only
> 1.4x, because `System.Text.Json` shares a process-wide cache between *equivalent*
> instances. New options with *different* settings is 7.2x. So: reuse it, and above all
> don't vary its settings per call. The second mistake is the expensive one.

## Slide 26 — Plugin architectures and dynamic proxies · 1:30

**Visual:** diagram `17`; two bullet columns beneath.

**Say (proxies):**

> The caller holds an `IAccountService`. What it actually has is `generatedProxy_1` — a type
> created at *runtime* that implements the interface. Every interface call lands in one
> method: `Invoke`. That's where logging, caching, retries and timing go.
>
> Notice what that means: `DispatchProxy` is doing exactly what we did by hand four slides
> ago. It wrote the `TypeBuilder` code for us.
>
> And `AccountService.cs` contains no logging code at all.

**Say (the honest caveat — verbatim):**

> But be clear what metaprogramming gave us. It gave us the *seam*. It did not give us the
> *policy*. The demo cache has no expiry, no size limit, no invalidation and no thread
> safety. A real one needs all four. Same for authorization: a proxy can be *where* you
> enforce a policy; it doesn't supply the policy or make it correct. An interception
> mechanism that silently applies a wrong policy is worse than no interception.

**Say (limits):**

> Interfaces only. The base proxy must not be sealed. And the one that catches everyone: a
> self-call inside the service is *not* intercepted, because `this` inside the service is the
> real object, not the proxy. That breaks naive caching in a way that's hard to spot.
>
> Plugins, one line since we covered it: `AssemblyLoadContext` is not a sandbox, and
> `Unload()` is a request, not an action — one cached `Type` keeps the context alive forever.

**Transition:**

> Which brings us to the last technique — and the one I'd actually recommend.

## Slide 27 — Cross-cutting concerns and expression trees · 1:45

**Visual:** diagram `16`; two-line code box; seams table.

**Say (expression trees):**

> Two lines. Identical source text — `n => n > 18`. The only difference is the *type* I
> assigned it to.
>
> `Func` gives you compiled IL: you can call it, you can't read it. `Expression` gives you an
> object *graph* describing the lambda: you can read it, rewrite it, print it, translate it.
>
> Look at the tree. `AndAlso` at the root; `GreaterThan` and `Equal` beneath; member-access
> and constant nodes under those. Every node is a strongly typed object.
>
> Which means a library can ask: *which property is being compared, and to what?* That's
> exactly the question a SQL translator has to answer — and it's how the EF Core SQL two
> slides ago happened.
>
> And note both arrows reach the *same* parameter node — a graph with shared nodes, not a
> strict tree. Worth knowing before you write a visitor.

**Say (the recommendation — verbatim):**

> Compare with Reflection.Emit. Same speed class after compilation. But the expression
> version is type-checked *as you build it* — `Expression.Add` on an int and a string throws
> immediately, with a clear message. Remember what the IL version did there? Silently
> returned garbage.
>
> So: prefer expression trees whenever you need a *function*. Reach for Emit only when you
> need a *type*, which `Expression` cannot create.

**Say (seams):**

> Where does a cross-cutting concern go? Middleware for the HTTP request. Filters for MVC
> concepts. Proxies or decorators for a service interface. Source generators when the shape
> is known at build time.
>
> The test: would this still apply if the call came from a background job instead of HTTP?
> If yes, it belongs at the service seam.
>
> And the answer that's right more often than any of them: a hand-written decorator. Twenty
> lines of ordinary C# — debuggable, trimmable, AOT-safe, obvious. Reach for a generated
> proxy when the number of interfaces makes hand-writing impractical, not before.

## Slide 28 — Key takeaways, Q&A, references · 1:30

**Visual:** five takeaways, decision order, the three corrections box, "Questions".

**Say:**

> Five things.
>
> One. A .NET assembly is self-describing. Metadata is required, not optional, and reflection
> just reads it.
>
> Two — and if you remember one sentence from thirty-seven minutes, make it this. Discover
