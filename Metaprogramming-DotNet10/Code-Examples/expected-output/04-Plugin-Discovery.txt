4. UNLOADING A COLLECTIBLE AssemblyLoadContext
==============================================================================
Ran "monthly-sales" inside collectible context PluginALC:PluginDiscovery.Plugins.Sales
  first output line: Monthly sales for 2026-11
Unload() has been requested. Now the GC has to actually collect it.
  collection attempt 1: alive = True
  collection attempt 2: alive = False

Load context unloaded: True

What keeps a context alive (all of these are common mistakes):
  - any live instance of a plugin type
  - a cached Type, MethodInfo or Assembly from the plugin
  - a delegate pointing at plugin code (an event handler left subscribed)
  - a static field in the HOST holding any of the above

Also note: unloading frees managed state. It cannot undo side effects the plugin
already caused, and a plugin that P/Invoked into a native library may pin it.

==============================================================================
5. SECURITY AND VERSIONING - what this design does NOT give you
==============================================================================
AssemblyLoadContext is an ISOLATION boundary for TYPE IDENTITY and VERSIONS.
It is NOT a security sandbox. A loaded plugin runs with the host's full privileges.

Once you call LoadFromAssemblyPath on an assembly, that code can:
  - read and write any file the host process can
  - open sockets, start processes, read environment variables and secrets
  - use reflection against the host's own private state
  - call Environment.Exit and take the process down

There is no supported in-process sandbox in modern .NET. Code Access Security (CAS)
and AppDomain partial trust were .NET Framework features and are gone.

So: only load plugins you trust. If you must run untrusted code, isolate it at the
OS or platform level - a separate process with a reduced token, a container, a VM,
or WASM - not with an AssemblyLoadContext.

Practical hardening for a TRUSTED plugin model:
  - verify a strong name or Authenticode signature before loading
  - keep the contracts assembly tiny and version it deliberately
  - inspect metadata with MetadataLoadContext first (no code runs) and reject early
  - wrap every plugin call in try/catch; one bad plugin should not kill the host
  - log the assembly path, version and hash of everything you load
